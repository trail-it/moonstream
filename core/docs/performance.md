# 性能与复杂度报告

本报告只公布**实测数字**与测量方法，不预写任何"提升百分比"。基准代码在
[`core/perf/`](../perf/)，任何人都可以用同一条命令复现。

```bash
moon bench --target native --release core/perf
```

## 测量环境

| 项 | 值 |
|---|---|
| CPU | Intel64 Family 6 Model 154 Stepping 4，12 逻辑核心 |
| 操作系统 | Windows 10 Home China（build 26200） |
| MoonBit | `moon 0.1.20260713 (75c7e1f)`、`moonc v0.10.4+2cc641edf` |
| 后端 | native，release（C 后端 + 优化） |
| 计时 | `@bench`（10 批自动调参，报告 mean ± σ 与 min…max） |

**关于噪声**：这台机器是共享/虚拟化环境，同一基准在相邻两次运行之间的均值可以相差 2 倍
（例如 `scan_393B` 的均值在 94 µs 与 250 µs 之间浮动）。因此下文同时给出 **mean** 与 **min**，
并优先用**比值**（同一次运行内的对照）而不是绝对值来判断复杂度。

## 样本

`sample_document(n)` 生成一个包含 `n` 个对象的 JSON 数组，每项形如
`{"id":N,"name":"item-N","ok":true,"ratio":0.125}`，全部为 ASCII。
规模按对象数取 8 / 64 / 512 / 4096。

## 1. 扫描成本 vs 输入规模（线性性）

同一份输入一次性喂入，并调用 `finish`。

| 输入 | 字节 | 事件数 | MoonStream mean | MoonStream min | ns/字节（min） | `@json.parse` mean | 相对倍数（mean） |
|---|---:|---:|---:|---:|---:|---:|---:|
| 8 对象 | 393 | 90 | 219.84 µs | 198.85 µs | 506 | 19.93 µs | 11.0× |
| 64 对象 | 3 245 | 706 | 1.59 ms | 1.02 ms | 314 | 165.55 µs | 9.6× |
| 512 对象 | 26 917 | 5 634 | 13.56 ms | 12.86 ms | 478 | 3.15 ms | 4.3× |
| 4096 对象 | 223 061 | 45 058 | 109.56 ms | 65.60 ms | 294 | 26.07 ms | 4.2× |

结论：

- **ns/字节在三个数量级上基本恒定（约 300–500 ns/字节）**，没有出现随规模增长的次线性或超线性项。
  这是本项目唯一声明的复杂度性质：扫描成本与输入长度同阶。
- 事件密度稳定在约 0.20–0.23 个事件/字节。
- 相对核心库 `@json.parse` 慢 4–11 倍。差距来自 MoonStream 多做的工作：逐字段事件、
  每个事件携带 `Path` 与 `Span`、重复键检测、严格 UTF-8 与代理对校验、以及保留原始字节用于
  `CompletedDocument`。`@json.parse` 不做这些。
- 小输入上比值更高（11×），是因为固定开销占比大：解析 393 字节只有 200 µs，而每次调用都要
  构造解析器、事件数组与 `finish` 时的文本重建。

## 2. 扫描成本 vs 分块大小

同一份 512 对象文档（26 917 字节），预先切好块后只计时喂入循环。

| 分块 | mean | min |
|---|---:|---:|
| 1 字节 | 19.91 ms | 8.43 ms |
| 8 字节 | 13.94 ms | 10.43 ms |
| 64 字节 | 9.92 ms | 4.10 ms |
| 512 字节 | 13.31 ms | 12.11 ms |
| 4096 字节 | 8.96 ms | 4.23 ms |

结论：分块大小**不改变复杂度的量级**；极端到逐字节喂入时约慢 2 倍，这是每次 `feed` 的固定
开销（状态检查、事件数组重置、增量刷新）造成的，而不是重复扫描——总字节数没有变化。

## 3. 部分树投影的额外开销

事件在计时之外先算好，只计时把它们应用到 `Preview`。

| 步骤 | mean | min |
|---|---:|---:|
| 解析 512 对象文档 | 12.96 ms | 11.28 ms |
| 把它的 5 634 个事件投影成部分树 | 3.84 ms | 1.50 ms |

结论：投影成本约为解析本身的 **30%**。UI 可以选择不建树（只消费事件），这部分开销是可选的。

## 4. 多调用路由

4 个各自独立的文档被切成 32 字节片段后交错喂入（共 3 464 字节、112 次 `feed`）。

| 场景 | mean | min | ns/字节（mean） |
|---|---:|---:|---:|
| 4 个交错调用 | 1.73 ms | 1.49 ms | 500 |

结论：路由开销与单文档解析同一量级——它本来就是"每个调用各自解析一遍"，额外成本只有
按复合键查表。

## 5. 内存口径

本报告**不声称精确的分配统计**：MoonBit 没有暴露稳定的分配计数器，`@bench` 也不测量内存。可以
给出的结构性事实是：

- 解析器保留收到的全部原始字节（`Parser` 内部的 `raw`），用于在 `finish` 时构造
  `CompletedDocument`；内存与文档长度同阶。
- `CompletedDocument::byte_length()` 等于文档字节数。
- `Preview::node_count()` 给出部分树保留的节点数，调用方可用 `Preview::clear()` 随时丢弃。

需要"解析完就丢原文"的场景属于后续工作（见 `design-decisions.md` D4）。

## 6. 如何解读

- 这是一份**回归基线**，不是性能宣传：未来任何改动都可以用同一条命令对比。
- 数字随机器、编译器与后端变化；请以自己机器上的 `moon bench --target native --release core/perf`
  为准。
- 没有对 wasm-gc / js 后端做同等基准：`moon bench` 可以跑其它后端，但本报告只记录 native，
  避免把不同后端的数字混在一起比较。
